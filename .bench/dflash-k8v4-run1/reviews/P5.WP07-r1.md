## Findings

### 1. [major] Env-mutating tests run in parallel and race each other — `cargo test` is flaky (~3%)

The three tests in `src/config.rs` (lines 96, 111, 132) all mutate the **process-global**
`HOME`/`EDITOR` variables (`set_var`/`remove_var` at lines 99, 115–116, 124, 136–137) with
no synchronization, and they are the *only* tests in the crate (the sole `#[cfg(test)]`
module — `grep -rn "cfg(test)" src/` → only `src/config.rs:58`). libtest runs them
concurrently on its thread pool (this box: `nproc` = 24), so they race on each other's
snapshot/restore windows. The module doc comment (lines 60–61) states the requirement —
"these tests must not run in parallel with anything else that reads or writes the
environment" — but nothing enforces it.

Reproduced against the committed test binary
(`target/debug/deps/encode_queue-66bc3db64df8af32`):

- `--test-threads 8`: **5 failures / 150 runs**
- default `cargo test` threading: **≥2 failures / 120 runs**, e.g.
  ```
  test config::tests::from_env_uses_configured_editor ... FAILED
  panicked at src/config.rs:139:9:
  assertion `left == right` failed
    left:  "/home/agent/.config/encode_queue/commands.txt"   ← real HOME: another test's restore_env won the race
    right: "/tmp/fake-home/.config/encode_queue/commands.txt"
  ```
  (another observed class: `from_env_home_unset_is_an_error` can instead get `Ok` when a
  sibling re-set `HOME` between `remove_var` and `from_env`.)

This makes WP07's acceptance criterion "`Config::from_env` is unit-tested with controlled
env; `cargo test` passes" hold only non-deterministically, and it will make WP10's
`cargo test` gate flake as well.

**Fix (stays inside `src/config.rs`, the only file WP07 owns):** either (a) hold a
`static ENV_LOCK: std::sync::Mutex<()> = Mutex::new(());` guard for the whole body of each
test (std-only, no dependency, no `Cargo.toml` change), or (b) extract a pure
`Config::from_vars(home: Option<&str>, editor: Option<&str>) -> Result<Config, ConfigError>`
and unit-test that with no env mutation at all, leaving `from_env` a two-line wrapper.
Option (b) is the cleaner testability fix.

### 2. [minor] Non-Unicode `HOME` behaviour is documented and handled, but untested

Decision 3 (non-Unicode `HOME` → `ConfigError::HomeUnset`) is correct in code:
`std::env::var("HOME")` (config.rs:28) returns `Err(VarError::NotUnicode)` for a
non-UTF-8 value and `.map_err(|_| ConfigError::HomeUnset)?` maps it without panicking.
But no test covers it. On Linux it *is* testable in-crate without new dependencies, e.g.
`std::env::set_var("HOME", std::ffi::OsString::from_vec(vec![0xff, 0xfe]))`
(available through the `OsString`-accepting `set_var`), asserting `Err(HomeUnset)`.
Related: the `#[error]` message "HOME environment variable is not set" (config.rs:52) is
slightly inaccurate for the non-Unicode case; the doc comment (config.rs:50–51) does
cover it, and ERR-05 says message text is not the API, so that part is informational only.
Add the test when fixing finding 1 (put it under the same env lock).

### 3. [minor] `nvim` default placement: decision is ownership-correct; coordinate with WP02/WP10

Worker decision 2 (default applied in `config.rs`, not in `Editor::new`) judged:

- **CONVENTIONS.md does not assign the default to `Editor::new`.** Its Target layout
  attributes it to the outbound adapter description (`outbound/editor.rs —
  EditorProcess: $EDITOR (default nvim)`), and the Behaviour contract likewise
  ("`edit` opens the queue in `$EDITOR` (default `nvim`)"). So the conditional major
  ("if CONVENTIONS.md says `Editor::new` applies the default") does not trigger.
- **The plan's WP07 scope itself mandates it here:** "parses `EDITOR` into an `Editor`
  newtype **(default `nvim`)**" (PLAN.md, WP07 — scope). WP07 *depends on WP01 only*
  (coverage table) and, per the API-freeze section, codes against the **frozen**
  `Editor::new(&str)` surface — which in this worktree is the verbatim WP01 scaffold
  (`src/domain/queue/mod.rs:67–70`, `Editor::new` stores the name as-is). WP07 owns
  only `src/config.rs`, so it cannot implement the default in `Editor::new`; deferring
  it would leave `EDITOR`-unset producing `Editor("")` against the frozen scaffold and
  fail WP07's own acceptance test. Applying the default at `config.rs:32–33`
  (unset/empty → `Editor::new("nvim")`, set → verbatim) is the only ownership-compatible
  reading. **Not a deviation — decision upheld.**
- **Residual coordination risk:** WP02's plan independently assigns "constructor
  applying the `nvim` default" to `Editor` (WP02 — scope). When WP02 lands, the
  `nvim` literal will exist in two files. That is safe *only if* WP02's default is an
  empty-input **fallback** (empty → `nvim`), which is idempotent against config.rs
  always passing the non-empty `"nvim"`; a constructor that overrode non-empty input
  would violate WP07's verbatim-parse requirement. Flag for the WP02 reviewer and for
  WP10 integration (dedupe the literal, e.g. a shared const once the module is wired).
