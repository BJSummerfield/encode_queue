## Findings

### 1. [minor] Masked EISDIR when `queue.lock` exists as an unremovable directory (P6.Z carry-over — reproduced; adjudicated **minor**, not major)

- **Reproduction (twice):** `mkdir $ENCODE_QUEUE_DIR/queue.lock`, then `start` → exit 1, `error: lock file I/O failed: could not acquire the queue lock after 3 attempts`; queue intact, nothing executed, no panic.
- **Root cause:** for a directory at the lock path, `File::create_new` fails with `AlreadyExists` (on Linux the `O_EXCL` existence check wins over `EISDIR`), so the code takes the stale-lock branch: `read_holder_pid` maps the EISDIR from `fs::read_to_string` to `None` via `Err(_) => None` (`src/outbound/lock.rs:120-124`), and the reclaim's `let _ = fs::remove_file(...)` swallows the EISDIR (`src/outbound/lock.rs:91`). Three identical attempts later the loop exits with the fresh, uninformative catch-all (`src/outbound/lock.rs:98-101`).
- **Adjudication:** the P6.F4 contract is satisfied — exit 1 (a refusal, not a wrong 3), no data loss, no panic, and the message is literally true (it did try 3 times). The defect is diagnostic quality only: the actionable cause ("a directory sits at the lock path; remove it") is hidden. A major requires a wrong exit code, data loss, torn write, or panic; none occur. → **minor**.
- **Fix:** make `read_holder_pid` distinguish I/O errors from parse failures (parse failure ⇒ stale/reclaim; I/O error ⇒ surface it), and carry the last real `std::io::Error` into the terminal `LockError::Io` instead of `other("…after 3 attempts")`.

### 2. [minor] No unit test covers whitespace-only `ENCODE_QUEUE_SHELL` (P6.F2 carry-over — behaviour verified correct end-to-end)

- **Behaviour (e2e, binary):** `ENCODE_QUEUE_SHELL="  "` behaves exactly as the `fish` default — empty queue: `start` exit 0 (default selected, nothing spawned); non-empty queue: clean `failed to spawn the shell` exit 1 with queue intact (fish absent here); `ls` unaffected. Implemented by the `Some(_) => Shell::Fish` arm of `Config::from_vars` (`src/config.rs:113-116`), matching the module doc (`src/config.rs:11-19`).
- **Gap:** `from_vars_shell_unset_or_empty_defaults_to_fish` (`src/config.rs:398-406`) iterates only `[None, Some("")]`; no test feeds a whitespace-only shell value (the `"   "` literal at `src/config.rs:296` is in the `ENCODE_QUEUE_DIR` arm). A regression of the `trim()` check at `src/config.rs:113` would flip `"  "` into `Shell::new("  ")` → `ShellInvalid` (exit 2) with no test catching it.
- **Fix:** add `Some(std::ffi::OsStr::new("   "))` to the loop in `from_vars_shell_unset_or_empty_defaults_to_fish`.

### 3. [minor] `rm` index errors are printed under the `invalid command:` prefix

- `rm 0` → `invalid command: invalid entry index '0': expected a positive integer` (exit 2); `rm 999` → `invalid command: no queue entry at position 999` (exit 2). The prefix comes from the `CliError::BadCommand` arm at `src/main.rs:66-70`, which P6.F1's D2' routes index errors through (`src/inbound/cli.rs:164-169`; `src/domain/queue/mod.rs:170-175`).
- The F1 contract (exit 2, stderr message, queue unchanged) is fully met — this is message wording only ("invalid command" is misleading for an index error). Nit recorded as minor.
- **Fix:** a dedicated `CliError` display/branch for index errors, or reword the `BadCommand` prefix to `error: {e}`.

### 4. [minor] CRLF lines are normalised: trailing `\r` silently dropped in `read_all`

- `str::lines()` (`src/outbound/queue_file.rs:75`) strips `\r\n` line endings, so a Windows-edited queue file loses its `\r` on the first parse: `ls` no longer prints it verbatim and `start` runs the command without it, and the file is rewritten LF-only on the first `drop_first`/`write_all`. Legacy `read_line`-based behaviour would have kept and run the `\r`.
- CRLF input is out of contract (the tool only ever writes LF-terminated lines; the `cli.rs` docs already call no-trailing-newline files out of contract, `src/inbound/cli.rs:245-247`), and the observed behaviour is benign (arguably more correct under `sh`). No corruption, no exit-code anomaly. Informational; at most document the normalisation in `queue_file.rs` docs.

## Notes / adjudications

- **Case 7a adjudication (missing-but-creatable parent dir):** the brief expects `add` to fail cleanly when `ENCODE_QUEUE_DIR`'s parent does not exist; the binding behaviour contract instead mandates directory creation ("The directory is created if missing", `plan/TASKS.md`; legacy bootstrap parity at `src/main.rs:44-53`). Observed `add` exit 0 with the tree created is contract-correct, so the brief's literal expectation is a misread, not a defect. The genuinely uncreatable cases (non-writable root → `Permission denied` exit 1; parent-is-file → `Not a directory` exit 1) fail cleanly with no partial file, as required.
- **`ls` on a missing queue file prints one `\n` (not empty stdout):** exit 0 + stdout exactly `"\n"`. This is a documented, supervisor-approved deviation ("supervisor decision 2026-10-16; deviation from the brief's 'stdout empty' wording", `tests/cli.rs:86-99`), pinned by the black-box test `ls_on_missing_queue_file_exits_zero_with_single_trailing_newline`; missing ≡ empty preserves byte-identical `ls` output between empty and missing files (legacy empty-file `ls` parity). Adjudicated acceptable.
- **`start` on a missing queue file exits 1** (`queue file not found at …`): intentionally preserved legacy behaviour (only `ls` was softened by P6.H; see `src/domain/queue/service.rs:115-120`). Correct per spec.
- **`rm` on a missing queue file exits 1** (I/O error, not 2): F1 specifies exit 2 only for parse-time and out-of-range cases; missing file is an I/O error. Consistent with the service docs.
- **Environment churn (not a product finding):** `target/release/` was wiped twice mid-review by sibling P7 reviewers running `$DEV cargo` in the same repo. Per orchestrator guidance, affected cases (9, 6, 8) were re-run guarded on the release path; the scratch binary used for the other cases is md5-identical to the fresh release build of the pinned source.
