## Findings

1. **[blocker] TY-03 / OP5 — `pub` fields on domain types** (`src/domain/shell.rs:24`, `src/domain/failure.rs:22,24,26`).
   TY-03's own How-to-check (`grep -rnE "^\s*pub [a-z_][a-z0-9_]*\s*:" src/ | grep -E "^src/domain/"` → expected empty) returns 4 hits: `ShellError { pub input: String }` and `FailureRecord { pub timestamp: u64, pub exit_code: i32, pub command: QueueEntry }`. OP5 (non-negotiable, "wins every conflict") says domain types "never `pub` fields", and the check's own annotation reads it as "no `pub` fields in the domain". The `FailureRecord` doc comment (`failure.rs:13-20`) justifies the fields with "OP5 targets fallible newtypes" — a re-interpretation the owner preference as written does not grant (OP5 says "Domain types", not "domain newtypes"), and which the convention's check command does not reflect. These are the only `pub` fields in the entire `src/` tree (grep outside `src/domain/` → empty).
   Fix: make the fields private and add constructors/accessors — e.g. `ShellError { input: String }` + `impl ShellError { pub fn input(&self) -> &str }` (callers: `config.rs:114` `e.input`; tests in `shell.rs`), and `FailureRecord::new(timestamp, exit_code, command)` + `timestamp()`/`exit_code()`/`command()` accessors (callers: `service.rs:195-200`, `queue_file.rs:153-159`, the two test suites). Re-run the TY-03 How-to-check until empty.

2. **[blocker] ARCH-02 — `main` performs file I/O** (`src/main.rs:21,44-52`).
   `fn main` (58 lines, `main.rs:29-86`) calls `fs::create_dir_all(queue_dir)` with an `eprintln!`+exit-1 error arm. ARCH-02's rule: `main` does "exactly" the five bootstrap steps, "No loops, no file I/O, no command parsing, no process spawning"; its How-to-check: "contains no `fs::`". The convention's own "Bad" example for ARCH-02 quotes the legacy main's `fs::create_dir_all` as the antipattern. The code's "Legacy bootstrap parity" comment shows the tension: the PLAN.md behaviour contract pins "dir created if missing" as behaviour, but pins *behaviour*, not placement — the contract's observable points (add-appends on a fresh `$HOME`, ls-prints, start-drains, edit-opens) are all preservable with the directory created inside the `FileQueueStore` adapter, where `OpenOptions`/`std::fs` already live (ARCH-03). PLAN.md's WP10 acceptance list never included ARCH-02's own How-to-check, so this shipped unreviewed against it.
   Fix: move the creation into `src/outbound/queue_file.rs` — a private `fn ensure_queue_dir(&self) -> Result<(), QueueStoreError>` (parent of the stored `QueuePath`, failure → `QueueStoreError::Io`) called from `append` (the contract's `add` behaviour) and, for byte-for-byte bootstrap side-effect parity, from `read_all`/`drop_first`/`write_all`; delete the `fs` block and `use std::fs;` from `main.rs`. Verify with the ARCH-02 How-to-check (no `fs::` in `main`, under ~40 lines) and the WP10 smoke behaviours.

3. **[major] DISP-04 — `delegate_run!` lacks the explicit empty-form rule** (`src/outbound/shell.rs:70-82`).
   The macro's single rule `($($variant:ident),* $(,)?)` admits a zero-argument call. Empirical check (scratch replica, `dev rustc --edition 2021`): `delegate_run!()` compiles to an empty `match self {}` and fails with `error[E0282]: type annotations needed` (plus an `unreachable_code` warning) — a cryptic diagnostic that does not name the macro or the missing input, exactly the "accidental zero-repetition expansion" DISP-04's rule and Bad example forbid. The How-to-check ("confirm the error message names the macro and the missing input") fails. Counterpart verified compliant: `impl_dispatch!`'s explicit `($port:ident for $enum:ident {})` rule emits `error: impl_dispatch! needs at least one variant` (scratch invocation).
   Mitigating context (why major, not blocker): `delegate_run!` is module-private with exactly one call site, in a non-degenerate form; the convention-mandated exported dispatch macro `impl_dispatch!` does carry the DISP-04 arm, so OP2's structural intent is met; the P6.F2 review brief recorded a sanction for this gap (carry-over context). The rule as written, however, does not exempt private or single-use macros.
   Fix: add before the general rule: `() => { compile_error!("delegate_run! needs at least one variant") };` (mirror `ports/dispatch.rs:32-35`).

4. **[major] DISP-02 literal miss + doc drift — production dispatch is generated by `delegate_run!`, leaving `impl_dispatch!` orphaned** (`src/outbound/shell.rs:83`; `src/ports/dispatch.rs:2-31,79`).
   DISP-02's How-to-check requires the multi-implementation enum's single `impl <Port> for <Enum>` to "come from an `impl_dispatch!` call". The production `impl CommandRunner for ShellRunner` comes from `delegate_run!` instead. Consequently `impl_dispatch!` is dead in production: its only invocation is in its own `#[cfg(test)]` module (`ports/dispatch.rs:79`, against a synthetic `Alpha`/`Beta` test enum), and its module doc — "implements a single-method port on a dispatcher enum … the shape of `CommandRunner`, the only port with multiple candidate implementations" (`dispatch.rs:2-31`) — still presents it as the dispatch mechanism, which is now stale and will mislead future readers about where the enumeration of `ShellRunner` variants lives. (Functional intent of DISP-02 — macro-generated arms, single impl, compiler-checked exhaustiveness — is met; the `todo!/unimplemented!` grep is empty.)
   Fix: either route the production dispatch through `impl_dispatch!` (generalizing its arm shape, e.g. accepting a variant→program mapping, so one macro is the single enumeration point) or retire `impl_dispatch!` and update `ports/dispatch.rs`'s doc to point at `delegate_run!` — and in either case apply finding 3's empty-form rule to whichever macro remains.
