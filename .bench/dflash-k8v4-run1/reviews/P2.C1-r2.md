## Findings

1. **[major]** TY-02 (CONVENTIONS.md, Types & parsing): the replacement regex
   `grep -rnE "fn [a-z_0-9]+ *\([^)]*: *(&str|String|&Path|PathBuf)\b" src/domain
   src/ports` is expected to be "→ empty", but it **false-positives on code the doc
   itself mandates in `src/domain/`**: `impl FromStr for QueueEntry { fn from_str(s:
   &str) → … }` (TY-01's own Good example, placed in `src/domain/queue/mod.rs`) and
   `impl TryFrom<&str> for QueueEntry { fn try_from(s: &str) → … }` (TY-04's rule and
   its own check "every `TryFrom`/`From` impl in `src/domain/`"). Verified live:
   scratch `src/domain/queue.rs` containing exactly the doc's prescribed compliant
   newtype + `FromStr` + `TryFrom<&str>` produced two matches
   (`queue.rs:9: fn from_str(s: &str)`, `queue.rs:17: fn try_from(s: &str)`, exit 0)
   under the verbatim check. A tree compliant with TY-01/TY-04 can never satisfy
   TY-02's "→ empty" — the check cannot pass on compliant code (same failure class as
   the round-1 major; the mandated parsing boundary is precisely where raw `&str`
   parameters are legal). Fix: carve out the parsing boundary in the check, e.g.
   `grep -rnE "fn [a-z_0-9]+ *\([^)]*: *(&str|String|&Path|PathBuf)\b" src/domain
   src/ports 2>/dev/null | grep -vE "fn (from_str|try_from)\b" → empty`, or state the
   expectation as "empty except one line per `from_str`/`try_from` parsing impl,
   which TY-01/TY-04 require". (The fix for the round-1 *miss* is otherwise good:
   named params after `&self` are caught and newtype params are not flagged — verified.)
2. **[minor]** Round-1 exit-2 fix does not achieve what the doc claims (ARCH-01,
   ARCH-03, TY-02, TY-03, TST-01 "How to check"). `2>/dev/null` redirects stderr but
   does not change the exit status: run verbatim today, every one of these commands
   still exits **2** (`grep: src/domain: No such file or directory` suppressed, status
   preserved) — identical exit behaviour to round 1. The doc's inline justification
   ("`2>/dev/null` keeps it runnable before `src/domain`/`src/ports` exist; today it
   is simply empty") is therefore inaccurate: the output is empty but the command
   does not run clean (exit 2 ≠ "no matches" exit 1). In the target state the
   commands work (exit 0/1 verified on scratch trees). Fix: gate the commands, e.g.
   `test -d src/domain && grep … ; test -d src/ports && grep …` (or `grep … || [
   "$?" -le 1 ]`), or copy the TST-01 "(Applies once the Target layout exists.)"
   framing to these five checks; drop the "keeps it runnable" claim.
3. **[minor]** TY-05 / GEN-04 factual error: "(it is a restriction lint, so the check
   is only meaningful once that `#![deny]` is present)" is wrong.
   `inherent_to_string_shadow_display` is **deny-by-default** (correctness) on this
   toolchain: clippy 0.1.98 errors on an inherent `to_string` shadowing `Display`
   with *no* deny attribute at all (exit 101) and still errors under `-- -A
   warnings` (exit 101, 3 errors); compiler note: "`#[deny(clippy::inherent_to_string
   _shadow_display)]` on by default". So the check was never vacuous, and the
   `#![deny(clippy::inherent_to_string_shadow_display)]` line in GEN-04's Good is
   redundant (harmless, self-documenting). Fix: replace the parenthetical with "deny
   by default (correctness group), so the clippy check is meaningful with or without
   the explicit `#![deny]`; the explicit deny is kept for self-documentation".
   (The round-1 finding it responds to was itself based on the restriction-lint
   premise; the functional outcome — enforced — is better than the doc claims.)
4. **[minor]** GEN-01 rule/check coverage gap: the rule forbids `unwrap`/`expect`/
   `panic!`/`unreachable!` outside tests, but the documented mechanism
   `#![cfg_attr(not(test), deny(clippy::unwrap_used, clippy::expect_used))]` only
   covers the first two. Verified: `clippy::panic` and `clippy::unreachable` are
   allow-by-default restriction lints (clippy `-W help` lists both under
   `clippy::restriction`), and a scratch crate with non-test `panic!()` +
   `unreachable!()` **passes** the documented check (exit 0). Verified fix: adding
   the two lints to the deny makes the same crate fail (exit 101: "usage of the
   `unreachable!` macro", "`panic` should not be present in production code"), while
   test-code `panic!` stays allowed via the same `cfg_attr(not(test), …)`. Fix:
   `#![cfg_attr(not(test), deny(clippy::unwrap_used, clippy::expect_used,
   clippy::panic, clippy::unreachable))]` in GEN-01/GEN-04/TST-03.
5. **[minor]** GEN-03 How-to-check aid is doubly broken: `grep -rnE
   "impl(Debug|Display|Error)" -A 15 src/ports` requires the group to stick directly
   to `impl` (no space), so it can never match valid Rust — verified live: it matches
   only `implDebug for Foo {}` and not `impl Display for Foo {}`/`impl Debug …`/
   `impl Error …` (exit 0 on the nonsense form, exit 1 on all valid forms). Even with
   the space added it would be vacuous for the rule's own bad example, because
   ERR-01 mandates `thiserror`-derived enums, which have no hand-written `impl
   Display/Error` line in source; the forbidden `&'a` payload sits in the `pub enum`
   declaration the grep never shows. Fix: make it a pure manual check ("review the
   variant payload fields of every error enum in `src/ports/` and
   `src/domain/queue/mod.rs` for borrowed `&` types") or an aid that targets the
   declarations, e.g. `grep -rnE "#\[derive\(" -A 25 src/ports src/domain | grep -n
   "&'".`
6. **[minor]** ERR-02 check contradicts the doc's own rule and Target layout: "Manual:
   exactly one error enum per file in `src/ports/` and `src/outbound/`" — but the
   doc's layout puts all three per-port error enums in `src/ports/` (`queue_store.rs`,
   `command_runner.rs`, `editor.rs`) plus `QueueEntryError` in
   `src/domain/queue/mod.rs`, and `src/outbound/` files are expected to contain
   **zero** error enums (ERR-02's rule: "each adapter translates the failures it
   knows about into those variants"). Read literally, the check fails on the
   doc's own compliant target tree. Fix: "at most one error enum per file; each
   boundary's enum lives beside its port in `src/ports/`; adapters translate into
   port error enums and define none of their own; `QueueError` composes (never
   duplicates) them."
7. **[minor]** GEN-01 Bad example undercounts: "(current `src/main.rs`, four
   violations in one file)" lists four, but the file has **five** panic-prone
   call sites — `env::var("HOME").expect(…)` (:31), `get_one::<String>(…).unwrap()`
   (:39), `queue_path.to_str().unwrap()` (:54, omitted), `_ => unreachable!()` (:56),
   `status().expect("Failed to open editor")` (:113). Cosmetic; the rule and the
   verified clippy mechanism catch all five. Fix: say "five" and add the
   `to_str().unwrap()` to the list (or say "at least four").
