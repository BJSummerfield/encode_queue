## Findings (round 2)

### 1. [minor] `ls` byte-exactness depends on an unspecified line-splitting/serialization choice

The plan claims `ls` stays "byte-for-byte unchanged" / "prints … **verbatim**"
(PLAN.md:38-41, 59, 194), but the WP04 design (`read_all() -> Vec<QueueEntry>`
parsed per line, `ls` printing entries — PLAN.md:180-195, 375-377) does not
specify how the file's lines are split, and the two natural choices differ
observably. Ground truth (empirical, current binary): `ls` is
`println!("{}", fs::read_to_string(path))` (`src/main.rs:50-51`), i.e. **raw
contents plus one extra trailing `\n`** — a 12-byte file `echo hi\n   \n`
produced 13 output bytes (`od -c`: `e c h o   h i \n     \n \n`). With
`lines()`-style splitting (no trailing empty entry), the refactored `ls` prints
one fewer trailing newline for every file ending in `\n` — i.e. every file
`add` produces (which always writes with `writeln!`); a split that keeps the
trailing empty entry as a lenient `QueueEntry` (e.g. split on `\n`) would
reproduce `println!("{}", contents)` byte-for-byte in all cases (also preserving
`\r` bytes that `str::lines()` would strip). Neither is mandated, so a WP04/WP10
worker can "satisfy" the verbatim claim with an implementation that is not
byte-identical, and the WP10 smoke ("ls-prints … printed verbatim", PLAN.md:375-377)
would not catch it.
**Fix (docs-only):** one sentence in WP04 scope (and/or the contract `ls` bullet):
specify that `read_all`'s line splitting preserves a trailing empty entry (split
on `\n`, lenient `FromStr` accepts it) and `ls` prints each entry with a newline —
which reproduces `println!("{}", contents)` byte-for-byte — or explicitly name the
one-trailing-newline normalisation as an accepted difference.

### 2. [minor] The `create_dir_all` side effect on all subcommands is unowned

Current `main` runs `fs::create_dir_all(queue_dir)?` **before dispatching any
subcommand** (`src/main.rs:35`). Empirically, on a fresh isolated `$HOME`,
`ls`/`start` (which currently fail with exit 1) still leave
`.config/encode_queue/` created. The contract's block quote says only of `add`
"dir created if missing" (PLAN.md:21), and no WP scope or acceptance criterion
assigns `create_dir_all` to the refactored layout (Target layout annotates
`outbound/queue_file.rs` as "read/append/rewrite" only; WP04's scope names no
directory creation). The observable stdout/exit codes are unchanged either way,
so this is a filesystem-side-effect gap, but the plan's own "byte-for-byte as
today" + smoke criteria would not catch a `ls`/`start`/`edit` that no longer
creates the directory.
**Fix (docs-only):** one line in WP04 scope ("the store ensures
`.config/encode_queue` exists on every operation, matching `src/main.rs:35`") or
a directory-exists check in the WP01/WP10 isolated-`$HOME` smokes.
