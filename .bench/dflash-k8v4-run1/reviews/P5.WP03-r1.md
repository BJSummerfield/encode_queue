### 4. Macro hygiene (DISP-02..05) — PASS

`src/ports/dispatch.rs:30-53`:

- **Two rules, one per call form**: normal
  `($port:ident for $enum:ident { $($variant:ident),* $(,)? })` (trailing comma
  accepted) and the explicit zero-variant
  `($port:ident for $enum:ident {})`, ordered first so it wins for `{}`.
- **Zero-variant rule live-verified** in a throwaway copy (worktree untouched):
  appending `impl_dispatch!(CommandRunner for EmptyRunner {});` and running
  `cargo check --tests` yields
  `error: impl_dispatch! needs at least one variant` pointing at the call site —
  the message names the macro and the missing input, exactly the DISP-04
  how-to-check. (See finding #1 for a cosmetic extra diagnostic.)
- **Expansion = single `match`, one delegating arm per variant**
  (`dispatch.rs:40-51`): one `impl` block, one method,
  `match self { $( Self::$variant(inner) => inner.run(entry), )* }` — matches
  the DISP-02 "Good" example shape, satisfies DISP-05 (no generated control
  flow, no self re-invocation, no helper chain).
- **`$crate::` qualification present**: `$crate::domain::queue::QueueEntry` and
  `$crate::ports::command_runner::RunError` — fully qualified per DISP-03; the
  binary-crate module layout (`mod domain;`/`mod ports;` in `src/main.rs`)
  makes both `$crate::` paths valid, proven by the passing dispatch test.
- **Fragments bound once**: each `$variant` appears exactly once per arm
  (an `ident`), `$port`/`$enum` once each.
- **`@`-helpers**: none exist, so nothing needs `@`-privacy or
  `#[doc(hidden)]`. DISP-02's requirement is conditional ("keeps helper rules
  private"), and the plan's parenthetical restates the DISP rules, not an
  unconditional helper mandate; the DISP-02 "Good" example itself has no
  helpers. The module docs (`dispatch.rs:24-29`) document the hard-coded
  single-method signature and why (only `CommandRunner` has multiple candidate
  implementations; `QueueStore`/`EditorLauncher` are single-impl ports in this
  codebase). Accepted design decision.
- `#[macro_export]` (`dispatch.rs:29`): justified by the worker; it keeps the
  DISP-03 hygiene story (exported macro ⇒ `$crate::`-qualified deps) and no
  `unused`/`unused_macros` warning appears in any clippy output.

## Findings

1. [minor] `src/ports/dispatch.rs:34` — the zero-variant expansion emits a
   second, cosmetic diagnostic alongside the named error. Live-verified:
   invoking `impl_dispatch!(CommandRunner for EmptyRunner {});` yields both
   `error: impl_dispatch! needs at least one variant` (the intended, named
   error — DISP-04 how-to-check passes) **and**
   `error: macros that expand to items must be delimited with braces or
   followed by a semicolon` (Rust's byproduct for a statement-form
   `compile_error!` expanding in item position). The intended message is
   present and unambiguous, and the pattern matches CONVENTIONS.md's own
   DISP-04 "Good" example verbatim, so this is not a rule violation. Optional
   hardening for a later WP: wrap the compile_error in an item, e.g.
   `const _: () = { compile_error!("impl_dispatch! needs at least one variant") };`,
   which should suppress the extra diagnostic while keeping the named error.
2. [minor] `src/ports/dispatch.rs:83-88` — the dispatch test cannot detect a
   cross-wired expansion: both `Alpha::run` and `Beta::run` return `Ok(())`, so
   swapped arms (`Self::Alpha(inner) => inner2.run(…)`) would still pass. The
   identity mapping is trivially visible in the one-line macro pattern
   (review-verified), so risk is low, but a stronger test would give the mocks
   distinct observable outcomes, e.g. `Beta::run` returning
   `Err(RunError::Other(std::io::Error::other("beta")))` and the test asserting
   `Alpha` → `Ok` and `Beta` → that specific `Other` variant.
