## Findings

### 1. [major] `src/domain/queue/service.rs` is not part of the crate — no `mod service;` declaration exists anywhere

Evidence:

- `grep -rn "mod service" src/` → no match (only `mod config/domain/inbound/outbound/ports`
  in `src/main.rs:1-5` and the per-directory `mod.rs` files).
- `src/domain/queue/mod.rs` (the `domain::queue` module file) declares no `service`
  submodule, so `src/domain/queue/service.rs` is never compiled by cargo. Proof: the
  build's 13 dead-code warnings include every other scaffold item (`QueueEntry`,
  `QueuePath`, `Editor`, `QueueEntryError`, `RunError`, `CommandRunner`,
  `EditorError`, `EditorLauncher`, `QueueStoreError`, `QueueStore`) but contain
  **no warning for `QueueService`** — an unreferenced module emits no diagnostics.
- Plan WP01 scope: "Create the Target-layout tree as **compilable scaffolding** …
  The new modules are declared but not yet wired into `main`; **they must
  compile**." The service-layer module is the only new module that is not declared.
- The worker's self-report ("Service scaffold uses the three-generic
  `QueueService<R, C, E>` arity") is true of the file's *text* but the file is
  absent from the build, so the scaffold's frozen API surface (plan section
  "API-freeze") does not actually include it. The file's own doc comment
  ("the resulting `dead_code` warnings are expected scaffold-stage noise",
  `src/domain/queue/service.rs:10-12`) is factually wrong for the current build:
  the file emits zero warnings because it is not compiled.
- Downstream contract break: WP08 owns **only** `src/domain/queue/service.rs`
  (dependency table). Making that file compile requires adding `mod service;` to
  `src/domain/queue/mod.rs`, which is owned by **WP02** — a latent file-ownership
  violation in WP08 that the plan's ownership contract does not anticipate.

Fix (verified in a scratch copy): add one line to `src/domain/queue/mod.rs`
(a file WP01 owns): `pub mod service;`. The crate then compiles with 15 scaffold
warnings instead of 13 (adds `struct QueueService is never constructed` and
`associated function new is never used` at `src/domain/queue/service.rs`), all
tolerated at WP01 stage. No other change needed.

### 2. [minor] Extra files `src/domain/mod.rs` and `src/inbound/mod.rs` are not in WP01's owned-files list

- Cross-check of the diff against every WP's owned-files list (WP01–WP10): **no
  downstream WP owns either path** (WP02 owns only `src/domain/queue/mod.rs`;
  WP09 owns only `src/inbound/cli.rs`). No ownership collision, so not a major.
- CONVENTIONS.md Target layout tree lists `domain/queue/{mod,service}.rs`,
  `inbound/cli.rs`, `ports/{mod,…}.rs`, `outbound/{mod,…}.rs` but does **not**
  explicitly list `src/domain/mod.rs` or `src/inbound/mod.rs`. They are, however,
  unavoidable under Rust 2018 module resolution: the layout's own
  `src/domain/queue/mod.rs` and `src/inbound/cli.rs` cannot be reached from
  `mod domain;` / `mod inbound;` without a module file for each directory (the
  `src/domain.rs`/`src/inbound.rs` alternatives are equally unlisted). The worker's
  claim ("needed for 2018 module resolution") is correct; this is a plan omission,
  not a worker error. The `mod.rs` form is also consistent with the layout's
  existing `mod.rs` style (`domain/queue/mod.rs`, `ports/mod.rs`, `outbound/mod.rs`).
- Recorded so the plan-of-record deviation is visible. Disposition: acceptable as
  created by the serial root (WP01 is concurrent with nothing); recommend the
  plan be amended to list both files under the Target layout and WP01's owned
  files.
