### 1. [major] Behaviour contract is contradicted by WP02/WP04/WP09: trim + blank-rejection of `QueueEntry` is an unowned observable behaviour change

The plan's behaviour contract (inherited by every WP) says:

- PLAN.md:30-32 — "`add` writes the raw `<CMD>` verbatim followed by a newline
  (no trim/validation at the boundary yet — see V-TY-01/V-TY-08; validation is
  *added* but **must not reject the same inputs the queue currently accepts**
  in the preserved flows)."
- PLAN.md preamble — "Only P5/P6 may change the specific bug behaviours named
  below," where the named behaviours are exactly the two Deferred items
  (V-ERR-09, V-ARCH-05 behaviour half).

But the WPs the same plan defines mandate rejecting exactly such inputs:

- PLAN.md:93-94 (WP02 scope) — `QueueEntry` with "`QueueEntryError::Empty` for
  blank input"; PLAN.md:100 (WP02 acceptance) —
  `QueueEntry::from_str("   ")` → `Empty`.
- PLAN.md:270-272 (WP09 scope) — "converts the raw `add` argument into a
  `QueueEntry` at the boundary (`QueueEntry::from_str(raw).map_err(CliError::
  BadCommand)`)".
- PLAN.md:294 (WP10 scope) — parse errors map to `ExitCode` 2.

Ground truth for the current behaviour (read of `src/main.rs:39-44` —
`writeln!(file, "{}", command)?` with no validation — and an empirical run of
the pre-built pre-refactor binary against an isolated `$HOME`):

```
$ HOME=$T target/debug/encode_queue add "   "
  exit=0
$ od -c $T/.config/encode_queue/commands.txt
  0000000                   \n   e   c   h   o       h   i  \n
$ HOME=$T target/debug/encode_queue ls
  (prints the 3-space line verbatim, then "echo hi")
```

The P3 audit documents the same as accepted current behaviour:
`docs/audit/types.md:75` (V-TY-01): "an empty or whitespace-only command can be
enqueued".

Consequences of executing the plan as written, none of which is covered by the
two named deferrals:

1. `add "   "` (and `add ""`): exit 0 + blank line enqueued **becomes** exit 2
   + nothing enqueued. Directly violates the PLAN.md:30 "verbatim" must-hold
   point and the "must not reject the same inputs the queue currently accepts"
   sentence.
2. `ls` on a queue file containing blank/whitespace lines (which the current
   `add` can produce): WP04's `read_all()` (PLAN.md:114-117) "parse[s] each
   line through `QueueEntry`'s `FromStr`", and the plan's
   `QueueStoreError::{QueueFileMissing, Io}` variant set (PLAN.md:68-70) has no
   malformed-line variant, so `Empty` lines must be skipped — `ls` would no
   longer print them, whereas current `ls` (`src/main.rs:50-51`) prints the
   raw bytes. Same family for whitespace-padded lines (canonical constructor
   trims, so `ls` output changes from the raw line to the trimmed one).

The plan's own preamble rule — "Where a P3 violation's *suggested fix* would
change one of these observable behaviours, the WP implements the structural
fix … but keeps the observable behaviour identical, and the behaviour change
itself is deferred to P5/P6" — is exactly what was done for V-ERR-09 and
V-ARCH-05, and exactly what was *not* done for the V-TY-01/V-TY-08 behaviour
half. As written, a worker following WP02/WP09 produces a binary that fails the
plan's own end-to-end smoke ("Behaviour contract holds end-to-end: … confirm
add-appends", PLAN.md WP10 acceptance).

**Fix (docs-only):** add a third Deferred entry, e.g. "V-TY-01/V-TY-08
behaviour half — `add` of empty/whitespace-only commands is accepted today
(exit 0, blank line enqueued); the trim + `Empty` rejection mandated by
WP02/WP09 changes `add` (exit 0→2) and `ls` (blank/padded lines omitted/
trimmed). Owner: P5 (or P6), consistent with the audits' suggested fixes", and
reference it from the scope of WP02, WP04, and WP09. Alternatively, amend the
WP02/WP09 boundary conversion so the inbound adapter accepts every input clap
currently accepts (i.e., document that `QueueEntry::new` trims but `add` does
not reject blanks until the owner phase decides). Either way the contract's
must-hold list and the Deferred list must agree.
